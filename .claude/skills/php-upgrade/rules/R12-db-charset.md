## 何が起きるか
新しい DB やドライバが UTF-8 を前提にしていると、EUC-JP のバイト列のまま格納したデータで、
- `LIKE` の一致判定（文字境界の解釈がずれて、ヒットしない・誤ってヒットする）
- 文字列関数（`length`、`substr`、`upper`/`lower`）
- 並び順（照合順序）
が変わる。SQLite 3 は文字列を UTF-8 として扱うため、SQLite 2（バイト単位）から移すと LIKE が壊れる（本リポジトリで確認済み）。
Symfoware の場合もデータベースの文字コード（EUC / UNICODE）を移行時に変えるなら同じ問題が起きる。

## 直し方（推奨）
**DB は UTF-8 にし、アプリとの境界（DB ラッパー）で変換する。** アプリのソースは EUC-JP のまま（UTF-8 化は 3D）。
1. データ移行スクリプトで、旧 DB の文字列を EUC-JP → UTF-8 に変換して新 DB に入れる。件数と主要列のハッシュ（変換前後で突き合わせ可能な形）を検証する。
2. DB ラッパーで、SQL 文とパラメータを UTF-8 に変換して送り、結果を EUC-JP に戻す。
3. 3D（UTF-8 化）のときはラッパーの変換を外すだけでよい。

## 落とし穴
- 旧 DB がバイト単位の LIKE だった場合、文字境界をまたいだ**誤ヒット**が起きていた可能性がある（EUC-JP の 2 バイト目 + 次の文字の 1 バイト目が検索語と一致する）。UTF-8 化でこれは起きなくなる。差分として分類案に書く。
- `LIKE` の大文字小文字の区別は DB ごとに違う（SQLite は ASCII のみ区別しない）。DB 製品を変えるなら確認する。
- 変換できない文字（機種依存文字、`～` の揺れ）がデータに含まれていないか、移行スクリプトで数える。
- 列の長さ制限（VARCHAR(100)）がバイト数か文字数かは DB による。UTF-8 にすると日本語 1 文字のバイト数が 2 → 3 に増える。

## 学び（実施記録）
- 2026-10-22-01: SQLite 3 に EUC-JP のバイト列を入れた状態で、商品名の部分文字列と第 1 水準漢字 3249 語を LIKE 検索すると、見逃し 115 件・誤ヒット 1349 件（例:「ボ」で 0 件）。UTF-8 にした DB では 0 / 0。`scripts/upgrade/tools/like-charset-check.php` で測れる。
- 2026-10-22-01: 既存の特性テスト（ボールペン、ノート B5 など）は**たまたま壊れない語**だったため、DB の文字コードの問題を検出できなかった。1 文字の検索や文字境界をまたぐ語のケースを足した（23, 24）。
- 2026-10-22-01: 旧の SQLite 2（バイト単位）でも、EUC-JP の文字境界をまたぐ誤ヒットがあった（「酬」で「表計算 ソフト 活用術」がヒット）。UTF-8 化で消えるので差分として上げる。
- 2026-10-22-01（振り返りで判明）: アプリ側の並べ替え（`strcmp` による EUC-JP のバイト順）は、DB から取った値を EUC-JP に戻してから並べているので変わらない。ただし **UTF-8 化（3D）で並び順が変わる**（解答キー E05）。DB の `ORDER BY` で日本語の列を並べている場合は、DB を UTF-8 にした時点で変わる。
