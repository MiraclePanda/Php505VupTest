# PHP 5.0.5 → PHP 8.5 アップグレードプロセス（初版）

Claude Code を使って、PHP 5.0.5 時代のアプリケーションを PHP 8.5 へ移行するための標準プロセス。
本リポジトリの `app/`（サンプルアプリ）を題材に検証し、改訂していく前提の初版である。

## 1. 基本方針

1. **振る舞いを先に固定する。** 移行前の応答を「特性テスト（ゴールデンマスター）」として記録し、移行後と機械的に比較する。テストがない状態でコードを書き換えない。
2. **旧環境で直せるものは旧環境で直す。** 5.0.5 上でも動く書き方への置換を先に済ませ、旧環境で特性テストが通ることを確認してから PHP 8.5 に切り替える。一度に変わる要素を減らすことで、差分の原因を特定しやすくする。
3. **互換性の移行と改善を混ぜない。** セキュリティ修正やリファクタリングは振る舞いを変えるため、互換移行とは別のステップ・別の PR にする。変えると決めた振る舞いは `docs/known-differences.md` に記録する。
4. **小さく刻んでコミットする。** 「1 つの移行ルール = 1 コミット」を原則とし、各コミットで構文チェックと特性テストを通す。エージェントの作業を人がレビューしやすく、戻しやすくするため。
5. **人が判断すべき点を明示する。** バグ互換にするか、仕様変更として受け入れるかはエージェントに決めさせず、判断待ちとして上げる。

## 2. 全体の流れ

| フェーズ | 内容 | 主な成果物 | 動作環境 |
|---|---|---|---|
| 0. 準備 | 旧環境の再現、ソースとデータの確保 | `docker/compose.legacy.yml`、本番相当の php.ini | 旧 |
| 1. 棚卸し | 移行課題の洗い出しと分類 | 課題一覧（`docs/inventory.md`） | ― |
| 2. 特性テスト | 旧環境の振る舞いを記録 | `tests/characterization/golden/` | 旧 |
| 3A. 前倒し修正 | 5.0.5 でも動く書き方へ置換 | コード修正（ルールごとのコミット） | 旧 |
| 3B. ランタイム切替 | PHP 8.5 で動かし、残課題を解消 | コード修正、既知差分一覧 | 新 |
| 3C. DB 移行 | ODBC 接続の継続か PDO_ODBC か、DB の世代交代（サンプルは SQLite 2 → 3） | 移行スクリプト、DSN 設定 | 新 |
| 3D. UTF-8 化 | EUC-JP → UTF-8（ソース・データ・画面） | 変換スクリプト、ゴールデンの取り直し | 新 |
| 3E. 改善（任意） | セキュリティ・保守性の改善 | 別 PR | 新 |
| 4. 受け入れ | 完了条件の確認 | チェックリスト | 新 |

## 3. フェーズ 0: 準備

- **ソース一式を Git 管理下に置く。** 本番サーバ上にしかないファイル（設定、`.htaccess`、cron スクリプト）も回収する。
- **本番の実行設定を入手する。** `php.ini`、Apache の設定、DB の接続設定（Symfoware の場合は ODBC の DSN 定義など）。特に `register_globals`、`magic_quotes_gpc`、`magic_quotes_sybase`、`short_open_tag`、`default_charset`、`mbstring.*` の値は振る舞いを大きく左右する。入手できない場合は当時の既定値を仮定し、その旨を記録する。
- **旧環境を Docker で再現する。** PHP 5.0.5 の公式イメージはないため、当時のディストリビューション（本リポジトリでは Debian etch）上でソースからビルドする。本番の DB は Symfoware（ODBC 接続）だが、検証用には SQLite の ODBC ドライバで代用する。アプリからは同じ `odbc_*` 関数で接続する。
- **テスト用データを用意する。** 本番データを使う場合は個人情報をマスクする。特性テストは決まったデータを前提にするので、初期化スクリプトで毎回同じ状態に戻せるようにする（`scripts/reset-db.sh`）。

## 4. フェーズ 1: 棚卸し

自動検出と目視を組み合わせ、課題を次の種別に分類する。サンプルアプリでの具体例は `docs/sample-app-traps.md` を参照。

| 種別 | 例 | 検出方法 |
|---|---|---|
| 実行設定依存 | register_globals、magic_quotes、短縮タグ | grep、php.ini との突き合わせ、目視 |
| 削除された構文 | 実行時参照渡し、`=& new`、`$s{0}` | PHP 8.5 での `php -l` |
| 削除された関数・拡張 | `ereg`、`split`、`each`、`create_function`、`session_register` | grep、PHPCompatibility（phpcs） |
| 意味が変わった仕様 | 数値と文字列の比較、PHP4 形式コンストラクタ、`htmlspecialchars` の既定値、`count(null)` | 静的解析だけでは漏れる。特性テストで検出 |
| 非推奨（8.x） | `(integer)` などの非標準キャスト名（8.5）、動的プロパティ（8.2） | PHP 8.5 で E_ALL 実行、PHPCompatibility |
| DB | DB 拡張の関数への直接依存、DB 製品固有の SQL、データファイル形式 | grep、DB 移行リハーサル |
| 文字コード | EUC-JP / Shift_JIS 前提の処理（`htmlspecialchars` の文字コード、`mb_*` の既定エンコーディング、`strlen` によるバイト数判定） | grep、特性テスト |
| セキュリティ | SQL インジェクション、XSS、MD5 パスワード | 目視、静的解析 |

自動検出の手段（導入時に PHP 8.5 対応状況を確認すること）:

- **`php -l`（PHP 8.5）**: 構文レベルの致命的エラーを全ファイルについて列挙する。`.inc` など拡張子が `.php` でないファイルも対象に含める。
- **PHPCompatibility（PHP_CodeSniffer）**: `--runtime-set testVersion 8.5` で、削除・非推奨の関数や構文を検出する。
- **Rector**: 機械的に置換できるもの（`each` → `foreach`、PHP4 コンストラクタなど）の自動修正に使える。ただし変更は必ず特性テストで確認する。
- **grep**: 実行設定に依存する書き方（`$HTTP_*_VARS`、`$PHP_SELF`、未定義のままの変数）は静的解析ツールでは拾いにくいため、パターンで探す。

## 5. フェーズ 2: 特性テスト（ゴールデンマスター）

旧環境に HTTP リクエストを送り、正規化した応答を `golden/` に保存する。移行後に同じリクエストを送り、差分を比較する。

**ケース設計の観点**

- 全画面の正常系（一覧、詳細、更新）と、ページング、検索条件の組み合わせ
- 空文字、未指定、不正値、日本語（全角スペース含む）、`'` `"` `<` `&` を含む入力
- 認証の有無による表示の違い、未ログイン時のリダイレクト
- 更新系は「更新 → 再検索」で DB への反映まで確認する
- 存在しない ID などのエラー経路

**正規化の方針**

- 日付、セッション ID、`Server` ヘッダなど、環境や時刻で揺れるものは落とすか置換する。
- ステータス行、`Location`、`Content-Type` は意味があるので残す。
- 正規化しすぎると差分を見逃すので、最初は最小限にし、揺れが出たものだけ追加する。

**運用**

- ゴールデンはコミットし、変更するときは理由をコミットメッセージに書く。
- 差分が出たら「回帰（直す）」「許容する仕様変更（`known-differences.md` に記録）」のどちらかに必ず分類する。分類は人が承認する。

## 6. フェーズ 3: 移行

### 3A. 旧環境上での前倒し修正

PHP 5.0.5 でも PHP 8.5 でも動く書き方に置き換える。各ステップのあと、**旧環境で** 特性テストを通す。

| 順序 | 置換内容 | 5.0.5 で可能か |
|---|---|---|
| 1 | 短縮タグ `<?` → `<?php`（`<?=` はそのままでよい） | 可 |
| 2 | `$HTTP_*_VARS` → `$_GET` / `$_POST` / `$_SERVER`、`$PHP_SELF` → `$_SERVER['PHP_SELF']` | 可 |
| 3 | register_globals 依存の除去（入力値を `$_GET` / `$_POST` から明示的に取得し、変数を初期化） | 可 |
| 4 | `session_register` 系 → `$_SESSION` | 可 |
| 5 | 実行時参照渡し、`=& new`、`$s{0}`、`(integer)` | 可 |
| 6 | PHP4 形式コンストラクタ → `__construct`、静的に呼ぶメソッドに `static` | 可 |
| 7 | `ereg` → `preg_match`、`split` → `explode` / `preg_split`、`each` → `foreach`、`create_function` → 名前付き関数 | 可（無名関数は 5.3 以降なので使わない） |
| 8 | `odbc_*` の呼び出しを DB ラッパー（`db.inc`）に集約し、プレースホルダ付きの `db_query($sql, $params)` を用意 | 可（内部は `odbc_prepare` / `odbc_execute` で実装） |
| 8b | 文字コードを暗黙の設定に頼らず明示する（`htmlspecialchars($s, ENT_COMPAT, 'EUC-JP')`、`mb_convert_kana($s, 's', 'EUC-JP')`、`header('Content-Type: text/html; charset=EUC-JP')`） | 可 |
| 9 | `magic_quotes_gpc` を Off にし、`stripslashes` を除去 | 可（旧環境の php.ini を変更して確認） |
| 10 | 旧環境の `register_globals` を Off にして特性テスト | 可 |

ステップ 9 と 10 は、旧環境の php.ini を新環境に近づける操作である。ここで特性テストが通れば、残る差分はランタイムの違いだけになる。

### 3B. ランタイム切替（PHP 8.5）

1. 必要なら `db.inc` の内部実装を PDO_ODBC（例外モード）に差し替える。`odbc_*` を使い続ける場合も、エラー処理を例外かログ出力に改める。呼び出し側は 3A-8 で集約済みなので変更は局所化される。
2. `error_reporting = E_ALL` で特性テストを実行し、Fatal、Warning、Deprecated をすべて解消する。
3. 意味が変わった仕様（数値と文字列の比較、`count(null)`、`htmlspecialchars` の既定フラグと既定文字コード、`default_charset`）による差分を確認し、回帰か仕様変更かを分類する。この段階では EUC-JP のまま動かし、特性テストを EUC-JP のバイト列で比較する。
4. 新環境での特性テストの結果を `known-differences.md` と照合し、記録のない差分がゼロになるまで繰り返す。

### 3C. DB 移行

本番は Symfoware に ODBC で接続している。サンプルでは SQLite の ODBC ドライバで代用し、SQLite 2 → SQLite 3 への世代交代を「DB のバージョンアップ」に見立てている。

- **接続方式を決める。** `odbc_*` 関数は PHP 8.5 にも残っているため、そのまま使い続けることもできる。PDO_ODBC に移すと、プリペアドステートメントと例外処理を PDO の流儀で書ける。どちらの場合も、文字列連結の SQL はプレースホルダに置き換える。
- **実行環境を用意する。** unixODBC、DB の ODBC ドライバ、DSN 定義（`/etc/odbc.ini`）を移行先に用意する。PHP 8.5 の公式 Docker イメージでは odbc 拡張のビルドに手当てが必要（`docker/modern/Dockerfile` 参照）。
- **データを移す。** 旧 DB からデータを抜き出し、新 DB に投入し直す。件数と主要列のハッシュを旧新で突き合わせる。
- **文字コードを確認する。** 新しい DB やドライバが UTF-8 を前提にしていると、EUC-JP のまま格納したデータで検索や比較の結果が狂う（サンプルでは SQLite 3 の LIKE で実際に起きる）。DB 側の文字コードを先に決め、アプリとの境界で変換するかどうかを 3D と合わせて判断する。
- **SQL 方言と ODBC ドライバの違いを確認する。** 列名の大文字小文字、`odbc_num_rows` が返す値、日付型の扱いなどはドライバによって異なる。

### 3D. UTF-8 化（EUC-JP → UTF-8）

互換移行（3A〜3C）で特性テストが一致してから、独立したステップとして行う。同時に行うと、差分の原因が PHP の仕様変更なのか文字コードなのか切り分けられなくなるため。

1. 特性テストの比較を「文字コードを UTF-8 に変換した上で比較する」モードに切り替え、ゴールデンを UTF-8 に変換したものを新しい基準にする。
2. ソースを UTF-8 に変換する（`iconv -f EUC-JP -t UTF-8`）。変換できない文字（機種依存文字、`～` と `〜` の揺れなど）を洗い出す。
3. 文字コードを明示している箇所（`'EUC-JP'` 指定、`<meta charset>`、`Content-Type`）を UTF-8 に変える。
4. DB のデータを UTF-8 に変換する。
5. バイト数で判定している箇所（`strlen` による長さチェックなど）と、並び順がバイト順に依存する箇所を確認し、仕様として扱いを決める。

### 3E. 改善（任意、別 PR）

互換移行が完了し、特性テストが通った状態を基準にして行う。

- SQL インジェクション対策（プリペアドステートメントの徹底）、XSS 対策（出力エスケープの徹底）
- パスワードハッシュの `password_hash` への移行（既存ユーザーは次回ログイン時に再ハッシュ）
- CSRF トークン、ログイン時の `session_regenerate_id`
- `include/` を公開ディレクトリの外へ移す
- Composer、オートロード、テストフレームワーク（PHPUnit）の導入

## 8. Claude Code での実行体制

### 8.1 リポジトリ側の仕掛け

| 仕掛け | 役割 | 状態 |
|---|---|---|
| `CLAUDE.md` | 作業ルール（1 ルール 1 コミット、テスト必須、改善を混ぜない）をエージェントに常に読ませる | 作成済み |
| 特性テスト（`tests/characterization/`） | 移行の合否判定 | 作成済み（ゴールデン未記録） |
| 旧環境・新環境の Docker | テスト対象の実行環境 | 作成済み |
| hooks（`.claude/settings.json`） | newapp の編集後に PHP 8.5 で `php -l` と文字コード検査を自動実行。`app/`・`golden/` の書き換えと解答キーの参照を拒否 | 作成済み |
| サブエージェント（`.claude/agents/`） | 下記の役割分担（`upgrade-inventory` / `upgrade-migrator` / `upgrade-verifier` / `upgrade-reviewer`） | 作成済み |
| スキル（`.claude/skills/`） | `php-upgrade`（手順、ルールカタログ、ノウハウ）、`upgrade-retro`（採点と学びの反映） | 作成済み |
| 道具（`scripts/upgrade/`） | EUC-JP の編集、構文チェック、register_globals 候補の検出、ルール別スキャン、検証一式 | 作成済み |

### 8.2 役割分担（案）

| 役割 | やること | やらないこと |
|---|---|---|
| 棚卸し担当 | 静的解析と grep で課題一覧を作り、種別と影響範囲を付ける | コードの変更 |
| 移行担当 | 課題一覧の 1 ルールずつ置換し、コミットする | 振る舞いの意図的な変更、改善 |
| 検証担当 | 環境を初期化して特性テストを実行し、差分を分類案付きで報告する | 差分の承認（人が行う） |
| レビュー担当 | 移行の差分を旧の php.ini と PHP 5.0 の意味で読み、振る舞いが同じかを確かめる | コードの変更 |

1 ルールごとに「移行 → 検証 → 差分があれば移行に戻す」を繰り返し、差分ゼロ（または承認済み差分のみ）になったら次のルールへ進む。

### 8.3 ゴールデンがない場合

旧環境を再現できず特性テストを記録できない場合は、棚卸しの直後に旧の応答を推定して `tests/characterization/expectations.tsv` に書き、
`scripts/upgrade/verify.sh` で照合する（`must` = 新でも成り立つべき、`legacy` = 移行で変わりうる旧の挙動）。
PHP エラーの有無だけでは、エラーを出さずに結果だけが変わる回帰を見逃す。ゴールデンを記録したら、推定が外れていた行を直す。

### 8.4 評価方法

サンプルアプリでは、解答キー（`docs/sample-app-traps.md`）をエージェントに見せずに移行を実行し、次の指標で評価する。プロンプトやハーネスを改善したら同じ条件で再実行して比較する。

- 検出率: 解答キーの項目のうち、棚卸しで見つけた割合
- 修正率: 特性テストが一致した、または差分が正しく分類された割合
- 誤修正: 特性テストで回帰として検出された変更の数
- 人の介入回数、所要時間、トークン消費量

結果と学びは `.claude/skills/php-upgrade/knowledge/`（`metrics.md`、`lessons.md`、`runs/`）に記録し、ルールカタログと手順に反映する（`upgrade-retro` スキル）。

## 9. 本リポジトリでの操作

```sh
# 旧環境（PHP 5.0.5）を起動して、ゴールデンを記録
docker compose -f docker/compose.legacy.yml up -d --build    # http://localhost:8050/
scripts/reset-db.sh legacy
tests/characterization/run.sh http://localhost:8050 tests/characterization/golden

# 新環境（PHP 8.5）で実行して比較
docker compose -f docker/compose.modern.yml up -d --build    # http://localhost:8085/
scripts/reset-db.sh modern
tests/characterization/run.sh http://localhost:8085 tests/characterization/actual
tests/characterization/compare.sh
```
